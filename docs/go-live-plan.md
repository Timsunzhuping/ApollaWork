# 上线计划

> 从「代码完成」到「可以交付企业客户」的路径。
> 部署操作见 [production.md](production.md)；已修缺陷清单见 [production-readiness.md](production-readiness.md)。

**核心判断**：代码层面已无明显欠账（148 测试、红队零缺口、越权/丢数据/挂起等真实缺陷已修）。
**剩下的不是继续写代码，而是在真实环境里验证** —— 尤其是阶段 0，它可能推翻后面一切。

每个阶段都有**出口条件**：不满足就不要进入下一阶段。

---

## 阶段 0 · 回答「产品到底行不行」

**为什么最先做**：黄金场景全部用 mock 模型（回放脚本）通过，证明的是平台管道通了，
**没有证明 Agent 能干成活**。真实成功率是未知数，而这是产品的全部价值。
不先回答这个问题，后面所有投入都是在赌。

| 事项 | 谁做 | 需要什么 |
|---|---|---|
| 在候选模型上跑真实评测 | 模型/算法 | 带 GPU 的机器 + 候选模型（Qwen3-32B / DeepSeek-V3 等） |
| 按失败场景调提示词与技能 | Agent 工程 | 上一步的失败样本 |
| 定默认模型与分档路由 | 架构 | 评测对比数据 |

```bash
MODEL_BASE_URL=http://<vLLM>/v1 MODEL_API_KEY=x MODEL_DEFAULT=<候选模型> \
  REPEAT=3 pnpm --filter @apolla/eval exec tsx live/run.ts
```

**出口条件**
- [ ] 真实成功率 **≥70%**（PRD §1.6 的 M1 线）
- [ ] 超时占比 <30%（否则结果不能作为能力结论 —— 见 [eval/live/README.md](../eval/live/README.md)）
- [ ] 单任务平均耗时与 token 成本在可接受范围，且已据此估算容量与预算

> **如果成功率 <70%**：不要硬上。两条路 ——
> ① 换更强的模型；② 把产品定位收窄（从「Agent 替你干活」改为「Agent 出草稿 + 人工确认」，
> 场景缩到通过率高的那几个）。第二条不丢人，比上线后被用户判死刑好。

## 阶段 1 · 打通生产执行路径

生产隔离靠沙箱容器，而 `EXECUTOR=docker` **一次都没跑过**。
开发用的 `local` 执行器把宿主 shell 开放给所有用户，绝不能上生产。

| 事项 | 谁做 | 需要什么 |
|---|---|---|
| 构建沙箱镜像 | 平台 | 能拉 Docker Hub 的网络，或内网镜像源 |
| 跑通 `EXECUTOR=docker` 全流程 | 平台 | 上一步的镜像 |
| 验证 ask 模式（审批下发）在容器下可用 | 平台 | — |

```bash
docker build -f infra/sandbox/Dockerfile -t apolla-sandbox:1.0 .
# 然后 EXECUTOR=docker SANDBOX_IMAGE=apolla-sandbox:1.0 起服务，跑一个任务
```

**出口条件**
- [ ] 容器模式下端到端跑通一个任务，产物正确
- [ ] ask 模式下审批能送达容器并让 Agent 继续（此前这条链路是断的，已修但未在真容器验证）
- [ ] 容器以非 root 运行、PID/内存/CPU 限制生效、无法访问白名单外网络

## 阶段 2 · 预发环境与真实依赖

| 事项 | 谁做 | 出口条件 |

**出口条件**

- [ ] 恢复演练成功，RPO/RTO 有实测数字（不是估计值）
- [ ] 真实 SSO 登录可用

## 阶段 3 · 内测

| 事项 | 谁做 | 说明 |
|---|---|---|
| 10–20 个真实用户，做真实工作 | 产品 | 不要用测试数据自嗨 |
| 每日看三个数 | 产品 | 任务成功率、**用户是否会用第二次**、最常失败的场景 |
| 按失败场景迭代技能与提示词 | Agent 工程 | 用真实失败样本，不是想象的场景 |

**出口条件**
- [ ] 连续两周任务成功率稳定 ≥70%
- [ ] 有用户主动重复使用（这比成功率更能说明产品价值）
- [ ] P0/P1 问题清零
